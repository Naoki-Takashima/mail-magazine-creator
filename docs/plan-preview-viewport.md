# プレビューのビューポート固定 + スマホモック表示

## 背景

現状、`main` は 2カラムの grid で、プレビュー列はページと一緒に流れる。
さらに `MailFrame` は `flex-1 h-full` でエディタ列の高さぶんまで引き伸ばされているため、
入力ブロックが 9つに増えた今、下へスクロールすると

- プレビューの見出し・メタ欄はページ上部に取り残される
- 巨大に引き伸ばされた iframe の「途中」だけが視界に残る

という状態になる。入力しながらプレビューを確認できない。

## 機能要件（ヒアリング確定）

1. プレビューは常にビューポート（100vh）の中に収まる
2. スマホ画面をイメージした枠の中にプレビューを表示する
3. プレビューの中身が収まらない場合、プレビューだけがスクロールする

### 確定した設計判断

| 論点               | 決定                                                                            |
| ------------------ | ------------------------------------------------------------------------------- |
| 600px 本体の見せ方 | **600px のまま描画して CSS `transform: scale()` で縮小**（横スクロールなし）    |
| スマホモックの意匠 | **既存テーマ準拠の簡素な枠**（墨色ベゼル / 角丸 / スピーカースリット / 落ち影） |
| 100vh 固定の方式   | **アプリシェル固定**（body を 100vh に固定し、エディタ列だけ内部スクロール）    |
| lg 未満            | **縦積みのまま**。スマホ枠に高さ上限（70vh）を付ける                            |

> 以降の「2. スマホモック」「3. 縮小表示」は初版の内容。
> 端末の縦横比と縮小率は実装後に見直しており、現行仕様は末尾の[追補](#追補実機比率への調整実装後のデザイン修正)を参照。

## 1. レイアウト方式：アプリシェル固定

ページ全体をスクロールさせるのをやめ、**ビューポートを 3段に割る**。

```
┌ AppHeader ─────────────────────────────┐ shrink-0
├──────────────────┬─────────────────────┤
│ EditorPanel      │ PreviewPanel        │ flex-1 / min-h-0
│   overflow-y-auto│   overflow-hidden   │
│   ▲              │   ┌─ PhoneMock ─┐   │
│   ║ ここだけ動く │   │ iframe 内部  │   │
│   ▼              │   │ スクロール   │   │
└──────────────────┴───┴──────────────┴───┘
```

`sticky + calc(100vh - ヘッダ高)` ではなくこの方式を採るのは、
**ヘッダの高さを CSS 定数として二重管理しなくて済む**ため。
ヘッダの padding を変えてもプレビューの高さは自動で追従する。

### 高さの連鎖（`min-h-0` を落とさない）

flex/grid の子は既定で `min-height:auto`（＝中身より小さくならない）。
1か所でも `min-h-0` を忘れると、エディタの中身の高さが親を押し広げて固定が破綻する。
`body → main → 各列 → PreviewPanel の中身` まで連鎖して指定する。

### 変更点

**`app/layout.tsx`**

```diff
- <body className="flex min-h-full flex-col">
+ <body className="flex min-h-full flex-col lg:h-full lg:overflow-hidden">
```

`lg:` 限定にすることで、小画面では従来どおりページ全体がスクロールする（要件4の決定）。

**`components/MailEditor.tsx`** — `main` に `lg:min-h-0` を追加。

**`components/editor/EditorPanel.tsx`** — 外側 `<section>` に
`lg:min-h-0 lg:overflow-y-auto` を追加。lg 以上では**この列がページのスクロール担当**になる。

- `overscroll-contain` を付け、エディタの末尾でホイールを止める（背後に動くものが無いため、慣性の抜けを防ぐ）
- スクロールバーが出て内容幅が変わるので、`scrollbar-gutter: stable` で入力欄の横幅が揺れないようにする

## 2. スマホモック（新規 `components/preview/PhoneMock.tsx`）

既存テーマ（紙 `#f4f1ea` / 墨 `#17150f` / 朱 `#c1440e`）に馴染む、装飾を絞った端末枠。
リアルなガラス表現やステータスバーは校正刷りの世界観とぶつかるため入れない。

```
   ╭────────────────────╮
   │        ▬▬▬         │  スピーカースリット（墨のうすい線）
   │ ┌────────────────┐ │
   │ │                │ │  ← 画面（白）。ここに MailFrame
   │ │   mail body    │ │
   │ │                │ │
   │ └────────────────┘ │
   ╰────────────────────╯
      ○ 390 × auto        端末幅のキャプション（mono・小）
```

- ベゼル: `bg-ink` + `rounded-[2.25rem]` + `p-2.5`、内側に薄い枠線で厚みを出す
- 影: `shadow-[0_30px_60px_-30px_rgba(23,21,15,0.65)]` の1枚に絞る（多重の白い影は使わない）
- スピーカースリット: 幅 40px / 高さ 4px / `bg-white/25` の角丸
- 画面: `rounded-[1.75rem] overflow-hidden bg-white`
- 端末の縦横比は**固定しない**。列の高さいっぱいに伸ばして視界を有効に使う
  （実機の 390×844 に固定すると、縦長ディスプレイで下が空き、短い画面ではみ出す）
- キャプションに実効表示幅（`600px → 390px` 相当）を mono で小さく添える。
  「今どのくらい縮んで見えているか」が分かるとレビュー時に迷わない
- `aria-hidden` は付けない。中の iframe には従来どおり `title` があるため、枠自体は装飾として `<div>` で置く

## 3. 縮小表示（`components/preview/MailFrame.tsx` + `app/globals.css`）

メール本体は `width:600px; max-width:100%` の table。
iframe を 390px にすると、3カラムの固定幅セル（176px × 3 + gap）がはみ出して
横スクロールが発生する。そこで **描画は 600px のまま、見た目だけ縮小**する。

変数は `:root`（`@theme`）に置く。PhoneMock と MailFrame の両方から参照するため、
クラスに閉じ込めない。

```css
@theme {
  /* buildMailHtml の MAIL_WIDTH と対応。両方を変えるときは揃える */
  --mail-width: 600px;
  /* 600px を 390px（iPhone の論理幅）に落とす倍率 */
  --phone-scale: 0.65;
}

/*
 * 枠ごと入らない幅では倍率を下げる（600 * 0.5 = 300px）。
 * 条件は Tailwind の max-[480px]（キャプション）と同じ形にして、
 * ちょうど 480px のときに倍率と表示がずれないようにする。
 */
@media not (min-width: 480px) {
  :root {
    --phone-scale: 0.5;
  }
}
```

```tsx
// ベゼルの内側がちょうど「メール幅 × 倍率」になるよう、左右の padding 分を足す
<div style={{ maxWidth: 'calc(var(--mail-width) * var(--phone-scale) + 1.25rem)' }}>
  <div className="relative min-h-0 flex-1 overflow-hidden">
    <iframe
      style={{
        width: 'var(--mail-width)',
        // 縮小前の高さ。× 倍率でちょうど枠の高さに戻る
        height: 'calc(100% / var(--phone-scale))',
        transform: 'scale(var(--phone-scale))',
      }}
      className="absolute top-0 left-0 origin-top-left border-0"
    />
  </div>
</div>
```

- `transform-origin: top left` で左上を固定し、はみ出しは親の `overflow-hidden` で切る
- **縦スクロールは iframe が自前で持つ**（要件3）。親側にスクロール領域を足さない
- 倍率は CSS 変数1か所。将来「PC / スマホ幅の切替」を足すときはこの変数を差し替えるだけで済む
- `zoom` ではなく `transform` を使うのは、`zoom` だと iframe 内部のレイアウト幅まで変わり
  「600px のメールとしての見た目」が保証できないため

## 4. プレビュー列の再構成（`components/preview/PreviewPanel.tsx`）

固定高になるぶん、列の中の縦の取り合いを明示する。

| 要素                            | 高さ                                            |
| ------------------------------- | ----------------------------------------------- |
| 見出し（Render / プレビュー）   | `shrink-0`。padding を `pt-8` → `pt-6` に詰める |
| `PreviewMeta`（配信日時・件名） | `shrink-0`。常時見えるままにする                |
| `PhoneMock`                     | `flex-1 min-h-0`（余りを全部取る）              |

- 列自体は `lg:h-full lg:min-h-0`
- lg 未満は縦積みで列の高さが中身で決まらないため、枠に `h-[70vh]` を直接与える
  （`flex-1` の `basis:0%` は高さ不定の親では解決できないので、`grow basis-auto` + `lg:basis-0` にする）。
  1画面に2つのスクロール領域を作らないよう 100vh にはしない
- 縦組みの `Live Preview` ラベルは残す（列が固定になっても位置がずれない）

## 追補：実機比率への調整（実装後のデザイン修正）

初版は端末枠を列の高さいっぱいに伸ばし、縮小率を 0.65 固定にしていた。
結果として枠が横に広く「iPhone に見えない」ため、以下を変更した。

- **プレビュー列の見出し（`Render` / `プレビュー`）をトルツメ**。浮いた約 90px は端末枠に回す。
  見出しが消えるぶん、`<section>` の名前は `aria-labelledby` から `aria-label="プレビュー"` に変更
- **画面の縦横比を iPhone 16 の論理解像度（393:852）に固定**。上下のベゼルを 20px、左右を 10px にして
  スピーカースリットぶんの偏りを無くし、内側の角丸もベゼルの厚みだけ小さくして外周と同心にした
- **大きさは「使える高さ」から逆算**する。高さ → 幅 → 縮小率の順に決まるため、
  倍率固定・メディアクエリ切替をやめた

### 縮小率の計算に実寸が要る理由

縮小率は `画面幅 ÷ 600px`、つまり長さ同士の比（無次元の数）で、CSS では作れない。
`aspect-ratio` で形は保てても、その結果の幅を `scale()` に渡す手段が無い。

そこで `hooks/useElementSize.ts`（`ResizeObserver`）で**端末枠に使える領域の実寸だけ**を測り、
`PhoneMock` が幅・高さ・`--phone-scale` を計算してインラインで渡す。
CSS 側の `--phone-scale` は計測前のフォールバック（0.65）として残す。

- 計測前は上限値（画面 390px / 倍率 0.65）で描くので、SSR と初回描画の内容は一致する
- リサイズで変わるのは端末枠のサイズだけ。`srcDoc` は同一参照で渡るため iframe は再読み込みされない
- 併せて `MAIL_WIDTH`（600）を `lib/buildMailHtml.ts` のローカル定数から `types/mail.ts` へ移し、
  HTML生成と縮小率が同じ値を見るようにした

### 追補2：iframe のビューポート幅を 624px に修正

スマホ枠に載せたところ、**左に本文背景の帯が 6px 出て、右はカードが画面端で切れる**という
左右非対称が出た（スクリーンショットの画素解析で確認）。

原因は iframe の幅を 600px にしていたこと。

```
iframe 600px
  → body padding 12px x 2 を引いて 576px
  → カードは width:600px だが max-width:100% なので 576px 止まり
  → セル padding 24px x 2 を引いて 528px
  → 3カラムの固定幅テーブルは 552px 必要 → 24px はみ出す
```

`MAIL_CONTENT_WIDTH(552) = MAIL_WIDTH(600) - セル padding 24 x 2` なので、
**カードが 600px になれる幅 = 600 + body padding 12 x 2 = 624px** が正しいビューポート幅。

- `types/mail.ts` に `MAIL_BODY_PADDING_X / Y` と `MAIL_VIEWPORT_WIDTH`(624) を追加し、
  `buildMailHtml` の body 余白もこの定数から組む（生成HTMLは従来と同一）
- `MailFrame` の iframe 幅を 624px に、`PhoneMock` の縮小率も 624 基準に変更
- 画面幅の上限を 390px → **393px**（iPhone 16 の論理幅そのもの）に。
  624 × 0.6298 = 393 で画面にちょうど収まり、カードの左右に 7.6px ずつ均等な余白が出る
- キャプションの比較対象は画面幅ではなく**カードの見た目の幅**（600px → 378px）に変更

補足: 古典的なスクロールバー（幅を取るタイプ）の環境では body の幅がその分削られ、
再び 552px を割ってはみ出す。macOS / iOS / Android の重ね表示スクロールバーでは起きない。
→ 追補3 でこの穴も塞いだ。

### 追補3：プレビュー用HTMLを分ける（body 余白とスクロールバーを外す）

追補2 の状態では、カードの左右に body の余白（12px）が残り、上には 24px の余白が乗る。
端末画面に載せると**右下にずれて見える**ため、プレビューではこの余白を落とすことにした。

`buildMailHtml(data, { forPreview: true })` を追加し、プレビューに渡すHTMLだけ

- `body` の `padding` を外す（カードが画面の端まで広がる）
- `html { scrollbar-width: none }` を入れてスクロールバーを消す

配信用（既定）は従来どおり `padding:24px 12px` を持ち、スクロールバー用のスタイルも入らない。

余白が無くなったぶん **iframe の幅は 624px → 600px に戻る**（`MAIL_VIEWPORT_WIDTH` は削除）。
600 × 0.655 = 393 で、カードが画面幅ちょうどに収まる。

スクロールバーを消したのは見た目のためだけではない。幅を取るスクロールバーは body を細くし、
カードが 600px に届かなくなって**カラムボックスの固定幅セルがはみ出す**。
実機の画面にスクロールバーは出ないので、忠実さの面でも消すのが正しい。

実測（縦の付属物を差し引いた概算）:

| ビューポート高 | 端末枠    | 画面      | 比率   | 縮小率 |
| -------------- | --------- | --------- | ------ | ------ |
| 768px          | 250 x 539 | 230 x 499 | 0.4609 | 0.369  |
| 900px          | 311 x 671 | 291 x 631 | 0.4612 | 0.466  |
| 1080px         | 394 x 851 | 374 x 811 | 0.4612 | 0.599  |
| 1440px         | 413 x 892 | 393 x 852 | 0.4613 | 0.630  |

（iPhone 16 の画面比 = 0.4613。上限は画面 393 x 852 = 実機の論理解像度そのもの）
