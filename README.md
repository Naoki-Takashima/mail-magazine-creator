# mail-magazine-creator

メルマガのコンテンツを入力すると、HTMLメールとしての見た目をその場で確認できるツール。

左が入力、右がプレビュー。入力すると約200msでプレビューが更新され、ページのリロードは不要。プレビューは開閉できる。

プレビューはスマートフォンの枠に載せた状態で**常に画面内に固定**され、入力をどれだけ下へ進めても隠れない。入力の最後にある「HTMLを出力」で、`YYYYMMDD_hhmm.html`（配信日時）としてダウンロードできる。

## 入力ブロック

| #   | ブロック                       | 入力                                                                                    | 必須 | メール本文への出力                                         |
| --- | ------------------------------ | --------------------------------------------------------------------------------------- | ---- | ---------------------------------------------------------- |
| 01  | 配信日                         | 日時（内部表現は `YYYYMMDDhhmm`）                                                       | ○    | 出さない（プレビュー上部のメタ欄に表示）                   |
| 02  | 件名                           | テキスト                                                                                | ○    | 出さない（端末画面上部の件名バーに表示）                   |
| 03  | 帯バナー（最大1件）            | 画像パス / URL                                                                          | −    | メール最上部に600px全幅の画像。URLがあれば画像全体がリンク |
| 04  | 大バナー（最大3件）            | 画像パス / URL / ボタンURL / ボタンテキスト / 文字色 / 背景色                           | −    | 1カラムで縦積み。画像＋任意のボタン                        |
| 05  | 3カラムボックス（最大3セット） | セットごとに タイトル / タイトル文字色、アイテム最大18件、ボタン最大3件                 | −    | 3カラム左寄せで並ぶ                                        |
| 06  | 2カラムボックス（最大3セット） | 同上（アイテムにノーマルテキストが加わる）                                              | −    | 2カラム左寄せで並ぶ                                        |
| 07  | 下部大バナー（最大5件）        | タイトル / タイトル文字色 + 04 と同じバナー入力                                         | −    | 1カラムで縦積み                                            |
| 08  | トピックスエリア（最大8件）    | タイトル / タイトル文字色、アイテム（URL / 画像 / 太字 / ノーマル / 文字色）、ボタン1件 | −    | 画像160px + テキスト376px の横並びを縦積み                 |
| 09  | インフォメーション（最大3件）  | URL / リンクテキスト                                                                    | −    | フッターに中央寄せで縦積み                                 |

- バナーは**画像だけでも表示**される（URL未入力ならリンクなし）。URLだけで画像が無い場合は何も出力しない
- 大バナーのボタンは、ボタンテキストがあり、かつ「ボタンURL または バナーURL」が有効なときだけ出力される（ボタンURLが空ならバナーURLを流用）
- ボタンの既定色は 文字 `#ffffff` / 背景 `#000000`

### カラムボックス（05 / 06）

「タイトル + カラムアイテム + 末尾ボタン」を1セットとし、セット自体を3つまで追加できる。

|                  | 3カラム     | 2カラム     |
| ---------------- | ----------- | ----------- |
| 列数 / 列幅      | 3列 / 176px | 2列 / 268px |
| 太字テキスト     | 最大10文字  | 最大15文字  |
| ノーマルテキスト | なし        | 最大26文字  |

- アイテムは **画像 / ロゴ / URL / 太字テキスト / テキストカラー**（2カラムはノーマルテキストも）
- **ロゴは任意**。指定するとメイン画像の直下に隙間なく繋がり、URLがあれば画像とロゴがまとめて1つのリンクになる
- 端数の行（3カラムに2件など）は空セルが幅を保持するため**左寄せ**のまま崩れない
- 末尾ボタンはコンテンツ幅いっぱい（552px）で縦積み。`ボタンURL` と `ボタンテキスト` が揃ったときだけ出力される
- 3カラム / 2カラムは構造が同型なので、型・リデューサ・UI・HTML生成をすべて共通化し、差分は `COLUMN_VARIANT_CONFIG`（`types/mail.ts`）1か所に集めている

### トピックスエリア（08）・フッター（09）

- トピックスは **画像160px + gap16px + テキスト376px** の横並び。テキストは左寄せ、アイテムは縦積みで、**2件目以降の上に1pxの区切り罫線**が入る
- 画像が無くてもテキストだけで出力される
- 末尾のボタンは1件のみ。`ボタンURL` と `ボタンテキスト` が揃ったときだけ出力される
- フッターのリンクは `#2563eb` + 下線の固定色。URLとテキストが揃った行だけ中央寄せで縦に並ぶ

## 設計メモ

### レイアウトはアプリシェル固定（lg 以上）

入力ブロックが9つあるため、ページ全体をスクロールさせるとプレビューがすぐ画面外へ流れる。そこで `lg` 以上では **body をビューポート高に固定**し、スクロールはエディタ列だけが内部で担当する。プレビュー列は1pxも動かない。

`sticky + calc(100vh - ヘッダ高)` にしなかったのは、**ヘッダの高さを CSS 定数として二重管理したくない**ため。この方式ならヘッダの padding を変えてもプレビューの高さは自動で追従する。

flex/grid の子は既定で `min-height:auto`（中身より小さくならない）なので、`body → main → 各列 → 端末枠` まで `min-h-0` を連鎖させている。**1か所でも落とすと入力の高さが列を押し広げて固定が壊れる**。

`lg` 未満は縦積みのまま。1画面に2つのスクロール領域を作らないよう、端末枠の高さを `70vh` に抑えている。

### プレビューは 600px で描画してから縮小する

メール本体は `width:600px` の table で、3カラムのセル幅（176px×3）は固定。iframe を実機幅（390px）にすると、はみ出して横スクロールになる。

そこで **描画は原寸（600px）のまま、`transform: scale()` で見た目だけ縮める**。幅の定数は `types/mail.ts` の `MAIL_WIDTH` に集約し、HTML生成とプレビューが同じ値を見ている。

カードは `width:600px; max-width:100%` なので、**iframe の幅が 600px を1pxでも下回るとカードが縮み**、コンテンツ幅が 552px を割って 3カラムの固定幅セルがはみ出す。これを踏まないよう、プレビュー用のHTMLでは次の2つを外している（`buildMailHtml(data, { forPreview: true })`）。

- **body の余白** — 端末画面の端までカードを広げる。残すとカードが 600px に届かない
- **スクロールバー** — 幅を取る種類のスクロールバーだと body がその分細くなり、同じくカードが縮む。実機の画面にスクロールバーは出ないので、見た目としても正しい

配信用のHTML（既定）は従来どおり `padding:24px 12px` を持ち、スクロールバー用のスタイルも入らない。

`zoom` を使わないのは、iframe 内部のレイアウト幅まで変わってしまい「600px のメールとしての見た目」を保証できないため。縦スクロールは iframe が自前で持つので、親側にスクロール領域は作っていない。

### HTML出力は配信用のHTMLを書き出す

出力するのは `buildMailHtml(data)`（オプション無し = 配信用）。プレビュー用との差は `body` の余白とスクロールバー用CSSだけで、**本文の中身は完全に同一**。件名は本文には出さず `<title>` に入れる。

ボタンは**バリデーションエラーが1件でも残っていれば disabled**。配信日時が無いとファイル名を作れないうえ、URLエラーを抱えたまま「リンクが抜けたHTML」を書き出す事故も防げる。理由は必須の欠け → URLエラーの順に1つだけ出す。

ダウンロードは Blob と `<a download>` だけ。サーバーには何も送らない。

### 件名は iframe の外に固定する

件名は HTML メールの中身ではなくヘッダ情報。`buildMailHtml` に入れると、将来「HTMLをコピー / ダウンロード」したときに本文へ混ざってしまう。

そこで実際のメーラーと同じく、**端末画面の上部に固定した帯（`SubjectBar`）**として親側で描いている。本文はこの帯の下をスクロールする。帯だけは縮小せず端末の等倍なので、プレビューを小さくしても件名は読める。

### 端末枠だけは実寸を測る

スマホ枠は **iPhone 16 の画面比（393:852）を保ったまま、使える高さいっぱい**に収まる大きさにする。高さから幅が決まり、幅から中身の縮小率が決まる。

この縮小率は「長さ ÷ 長さ」の無次元の数で、CSS では作れない（`calc(100cqw / 600px)` は書けない）。そのため `hooks/useElementSize.ts` の `ResizeObserver` で端末枠に使える領域の実寸だけを測り、`PhoneMock` が幅・高さ・`--phone-scale` を算出してインラインで渡している。

計測前は上限値（画面 393px / 倍率 0.655）で描くため、SSR と初回描画の内容は一致する。リサイズで変わるのは端末枠のサイズだけで、`srcDoc` は同一参照のまま渡るので iframe は再読み込みされない。

### プレビューは iframe の `srcDoc` で描画する

親ページの Tailwind（preflight を含む）がプレビューに漏れると「実際のメールの見た目」にならない。iframe でスタイルの境界をつくり、メール本文は table + インライン CSS で組んでいる。

`sandbox` からは `allow-scripts` を外してあるため、入力値がスクリプトとして実行される余地はない。

### HTML生成をコンポーネントから切り離す

`buildMailHtml(data: MailData): string` は React に依存しない純関数。将来「HTMLをコピー / ダウンロード」を追加するときは、この関数をそのまま再利用できる。

### XSS対策

- ユーザー入力はすべて `escapeHtml` を通す
- URLは `http:` / `https:` のみ許可（`javascript:` や `data:` は描画しない）
- **色は `escapeHtml` では守れない**。`style` 属性に差し込むため、`red;background:url(...)` のような値が別の宣言として解釈されないよう、`toSafeHexColor` で `#rgb` / `#rrggbb` 以外は既定色に倒している

ボタンテキストに `<script>alert(1)</script>` を入れても、文字列として表示されるだけ。

### 状態管理は `useReducer`

状態はネスト（帯バナー）と可変長配列（大バナー、カラムセット > アイテム / ボタン の3段）を含むため、更新ロジックを純関数 `lib/mailReducer.ts` に切り出して `useReducer` で束ねている。値を読むのは `EditorPanel` と `PreviewPanel` の2つだけなので、Context や状態管理ライブラリは使っていない。

カラム系のアクションはすべて `variant` を持ち、`COLUMN_VARIANT_CONFIG[variant].stateKey` で対象配列を決める。3カラム用・2カラム用にアクションを二重定義しないための作り。

入れ子リストの更新は `addToList` / `removeFromList` / `updateInList` の3ヘルパに集約している。上限チェックは `addToList` の中にあるため、UI の `disabled` とあわせて二重に守られる。

### 重複はブロックを増やすたびに共通部品へ寄せる

ブロックが9つになる過程で、同じ形の入力が繰り返し現れた。新しい型やコンポーネントを足す前に、既存を一般化して共用している。

- `LargeBanner` — 04 大バナーと 07 下部大バナーで型・HTML生成・入力カードをそのまま共用
- `ButtonContent` — 05 / 06 の `ColumnButton` から id を外した形。08 のボタン（1件のみ）と共用し、HTML生成も `buildBlockButton` 1本
- `TitleFields` / `buildBlockTitle` — 05〜08 のタイトル + タイトル文字色

デバウンスはプレビューの iframe だけに掛けている（`srcDoc` の差し替えは再読み込みを伴うため）。入力欄・メタ欄・件名バーは controlled のまま即時反映され、打鍵の遅延はない。
